= PCIM Named Requirements Plan

The <<oid-parity-plan>> records the November 4, 2026 analysis and proposed next
steps for this branch. Its lifecycle and completeness recommendations supersede
the earlier planning estimates and deprecated-identifier range below. It does
not assign official OIDs or change normative requirements.

== Purpose

This plan describes how to add named, traceable requirements to the PCIM
AsciiDoc source without adding implementation, product, container, reference UI,
or regulatory evidence artifacts to this repository.

The PCIM repository remains the source for:

* requirement identifiers and requirement text;
* metadata needed to extract requirements from AsciiDoc;
* references from requirements to PCIM actors, transactions, options, use cases,
  and message constraints;
* a generated requirements artifact that other tools can consume.

Downstream verification, implementation, deployment, and regulatory evidence
repositories should consume the exported PCIM requirements artifact. They should
not write implementation-specific artifacts back to this repository.

=== Duplicate And Overlap Reconciliation

The active connectathon workbook scenarios repeat the same protocol behaviors
across different participant combinations. Those repetitions should map to the
same PCIM requirement identifiers and separate test assertions, not to duplicate
specification requirements.

Current overlap decisions:

|===
|Overlap family |Disposition

|Actor narrative vs. transaction role table
|Keep actor-level requirements only for conformance claims or actor
responsibilities. Add transaction-level requirements only when the transaction
adds a distinct, independently testable behavior.

|Reporter validation status
|Keep the actor-level obligation to distinguish validated and unvalidated
assertions and keep the DEV-51 message-level obligation for the concrete
observation status encoding.

|Manager HMI
|Keep the profile-level HMI obligation for validation and conflict resolution.
Keep the DEV-51 HMI obligation only as the transaction-specific validation
workflow requirement.

|DEV-52 publication behavior
|Keep separate requirements for validated event notification, initial current
state delivery, matching filter delivery, correction publication, and
wrong-association publication because each has a different trigger or
acceptance condition.

|OBR-3 and OBR-29 rules repeated in transaction text and appendix text
|Use shared HL7 message-constraint requirements for common data rules. Add
transaction-specific requirements only when sender responsibility or update
semantics differ.

|Workbook scenario repetitions
|Map repeated checks in `PCIM_03`, `PCIM_04`, `PCIM_06`, and `PCIM_07` to the
same requirement identifiers and distinguish them by test scenario and assertion
identifier in downstream result artifacts.

|Obsolete or observational workbook tabs
|Do not create PCIM requirement identifiers from obsolete or observational tabs
unless the working group brings those scenarios back into scope.

|Explanatory `should` and `may` statements
|Do not create named requirements for implementation guidance unless the
statement is independently testable or tied to a declared optional capability.
|===

Before the first pull request, the review fixture should be checked for duplicate
identifiers and for obviously equivalent normative text. After this review, the
first pull request scope is 33 named PCIM requirements.

== Identifier Scheme

Use a PCIM-specific requirement identifier that is unique, stable, readable, and
compatible with the SDPi-style requirement-number pattern:

----
PCIMR0001
----

Proposed ranges:

|===
|Range |Use

|PCIMR0001-PCIMR0099
|Profile-level actor, transaction, option, and grouping requirements

|PCIMR0100-PCIMR0199
|DEV-51 requirements

|PCIMR0200-PCIMR0299
|DEV-52 requirements

|PCIMR0300-PCIMR0399
|DEV-19 requirements

|PCIMR0400-PCIMR0599
|Shared HL7 message structure and segment constraints

|PCIMR9000-PCIMR9999
|Deprecated or reserved identifiers
|===

Identifier rules:

* never renumber a published requirement;
* never reuse a deprecated identifier;
* preserve old identifiers in a deprecated-requirements artifact;
* use lower-case anchors for AsciiDoc navigation, for example `#pcimr0100`;
* use semantic cross-references instead of plain-text requirement numbers.

== AsciiDoc Markup Model

Follow the SDPi pattern, generalized for PCIM. A requirement block should have:

* a visible title containing the requirement identifier;
* a stable anchor;
* requirement level: `shall`, `should`, or `may`;
* requirement type;
* actor, transaction, option, use case, and message-field metadata when
  applicable;
* one normative statement;
* optional notes, rationale, and verification guidance.

Example:

----
.PCIMR0100
[pcim_requirement#pcimr0100,pcim_req_level=shall,pcim_req_type=tech_feature,pcim_actor=dpar,pcim_transaction=DEV-51,pcim_message=ORU_R01,pcim_segment="PID,PRT,OBR-7,OBR-8",pcim_use_case="uc1_associate_device_patient,uc2_disassociate_device_patient",pcim_verification_method=test,pcim_verification_level=connectathon]
****
[NORMATIVE]
====
The Device-Patient Association Reporter shall include the patient identifier,
device identifier, and association event timestamp in each association or
disassociation assertion.
====

[VERIFICATION]
====
Verify by inspecting a DEV-51 ORU_R01 message and confirming PID, PRT, OBR-7,
and OBR-8 content according to the PCIM message constraints.
====
****
----

If the existing SDPi converter is reused before it is generalized, a temporary
compatibility layer may map `pcim_requirement` and `pcim_req_*` attributes to
the SDPi internal model. The PCIM source should retain PCIM names.

== Export Format

The primary generated artifact should be JSON because it is easy for
connectathon tooling, dashboards, and CI systems to consume.

Proposed generated files:

* `pcim-requirements.json`
* `pcim-requirements-deprecated.json`
* `pcim-use-cases.json`
* `pcim-transactions.json`
* `pcim-requirement-trace.json`

For requirements-management tool exchange, also support ReqIF XML export.
ReqIF is the best fit for open requirements interchange between independent
requirements-management tools. OSLC RM is a good fit later if a service API is
needed for live linked-data integration.

Minimum JSON fields:

== Connectathon Validation Contract

The PCIM repository should publish requirements and trace metadata. A third-party
connectathon validation tool should consume that metadata and produce verdicts.

Recommended result contract:

----
{
  "requirementId": "PCIMR0100",
  "requirementVersion": "<pcim-version-or-commit>",
  "testScenarioId": "PCIM_01",
  "testStepId": "210",
  "implementationUnderTest": "<vendor-or-system-id>",
  "verdict": "pass",
  "evidence": [
    {
      "type": "message-capture",
      "uri": "<artifact-uri>",
      "hash": "<sha256>"
    },
    {
      "type": "validator-output",
      "uri": "<artifact-uri>",
      "hash": "<sha256>"
    }
  ],
  "timestamp": "<iso-8601>"
}
----

A green checkmark can be displayed for a requirement when all mandatory
assertions mapped to that requirement have a `pass` verdict for the declared
actor, option, and transaction scope. A failed or missing mandatory assertion
should produce a red failure or gray not-run status. Recommended (`should`) and
permitted (`may`) requirements should be reported separately so optional
capability claims are visible but do not fail an implementation that does not
claim the option.

The result format can also be emitted as JUnit XML or Cucumber Messages for CI
and dashboard compatibility, but the source trace should remain the PCIM
requirement identifier.

== IEC 62304-Oriented V&V Metadata

The PCIM repository should not store product-specific IEC 62304 evidence, but it
can provide metadata that lets other repositories create IEC 62304-compatible
traceability.

Recommended requirement metadata:

* `verification.method`: `inspection`, `analysis`, `test`, or `demonstration`;
* `verification.level`: `unit`, `integration`, `system`, or `connectathon`;
* `evidenceExpected`: expected evidence classes, such as message captures,
  validator outputs, logs, screenshots, risk-control review, or manual monitor
  attestation;
* `riskRelevance`: `safety`, `effectiveness`, `security`, or `interoperability`;
* `optionScope`: empty for mandatory profile behavior, or the PCIM option name
  when optional behavior is claimed.

This gives downstream V&V tools stable hooks for IEC 62304-style traceability:
requirement -> design element -> test case -> test run -> evidence -> verdict.

=== SDPi Findings

https://profiles.ihe.net/DEV/SDPi/index.html[SDPi Appendices 3:C and 1:A.4]
establish a specification-owned hierarchy under `1.3.6.1.4.1.19376.1.6.2.10`.
Requirements use `.10.<requirement-number>`; transaction OIDs use `.4.<transaction-number>`.
Human identifiers coexist with generated OIDs. Material normative changes
receive new identifiers; retired identifiers are never reused. Conformity
versions and namespaces have separate versioning. Requirement metadata supports
types, levels, parent/sibling relationships, groups and fulfillment links.
Fulfillment points back to definitions. Some detailed traceability and testing
features remain future work, so the published model is not proof of complete
test coverage.

The arc summary lists `.12` for use-case support, but Section 3:C.11 describes
support beneath each profile OID. PCIM must specify that placement explicitly.
Section 1:A.4.2.1 also allows some obligation-level changes without new IDs;
PCIM should document its chosen compatibility policy.

The https://github.com/IHE/DEV.SDPi/blob/master/articles/sdpi-article-ihe-tf-asciidoc-cookbook.adoc[SDPi AsciiDoc cookbook],
Sections 4.3 and 4.7-4.11, describes the tooling pattern: semantic block metadata,
automatic OIDs for requirements and transactions, explicit `oid-arcs` for other
objects, full OIDs for externally assigned objects, generated summary tables,
semantic cross-references, and deprecation exports with reuse checks.
This supports retaining PCIM's existing identifiers while adding machine identity.

==== Checks and Generation Actually on the CI Path

The {sdpi-ci-source}/.ci/asciidoc-converter/src/main/kotlin/org/sdpi/ConvertAndVerifySupplement.kt[entry point]
runs the converter and an AsciiDoc diagnostic checker, exiting with status 1
on an exception. The
{sdpi-ci-source}/.ci/asciidoc-converter/src/main/kotlin/org/sdpi/asciidoc/extension/SdpiInformationCollector.kt[information collector]
uses throwing checks for duplicate requirement IDs, duplicate OIDs among the
objects it enumerates, reuse of recorded deprecated requirements/transactions,
and various entity/reference constraints. It also requires normative content
and exactly one lower-case obligation keyword matching the declared level,
with none of the other two keywords. These checks run during collection.

The {sdpi-ci-source}/.ci/asciidoc-converter/src/main/kotlin/org/sdpi/asciidoc/extension/ReferenceMacroProcessors.kt[semantic reference processors]
reject unresolved supported reference targets. The separate
{sdpi-ci-source}/.ci/asciidoc-converter/src/main/kotlin/org/sdpi/asciidoc/AsciidocErrorCheck.kt[diagnostic checker]
recognizes selected stderr prefixes (`information:` and `info:`) and applies
reference exceptions; it is not a general all-warning or comprehensive HTML
link validator. Do not infer that any logged error necessarily fails CI:
the relevant throwing check or recognized diagnostic must be traced.

The {sdpi-ci-source}/.ci/asciidoc-converter/src/main/kotlin/org/sdpi/asciidoc/AsciidocConverter.kt[converter]
registers {sdpi-ci-source}/.ci/asciidoc-converter/src/main/kotlin/org/sdpi/asciidoc/extension/PopulateTables.kt[table generation]
against the same collector used for JSON serialization. It exports profiles,
use cases, content modules, transactions, requirements and deprecation lists
into each output directory's `exported-artifacts` folder. Thus shared-model
generation is verified; an independent HTML-versus-JSON equality check is not.

The collector also confirms the `.12` placement: profile use-case support is
formed from each profile OID plus `.12`, resolving the documentation ambiguity
noted above. Its duplicate-OID loop does not enumerate profile use-case-support
OIDs, so PCIM should explicitly cover every category in its registry checks.

==== What Is Not an Established SDPi CI Gate

The {sdpi-ci-source}/.ci/asciidoc-converter/src/test/kotlin/org/sdpi/TestRunner.kt[test helper]
compares generated HTML with expected fixtures, and
{sdpi-ci-source}/.ci/asciidoc-converter/src/test/kotlin/org/sdpi/ConvertRequirementsTest.kt[requirement tests]
exercise rendering and references. These tests exist but are not invoked by
the audited workflows. No explicit CI gate was found for exported JSON Schema
validation, export/appendix equality, normative-coverage accounting, comparison
against previous-release identities, parent-cycle detection, or stability after
source reordering. Current-source deprecation checks do not themselves prove
that a previously published identifier was preserved or explicitly retired.

The {sdpi-ci-source}/.github/prepare_artifacts.sh[artifact script]
runs a second Ruby Asciidoctor pass for diagrams/static assets and builds the
ZIP. It does not compare the exported model with the rendered appendix, and
does not enable shell fail-fast behavior. Its root-level temporary HTML is
removed; the Kotlin-generated HTML remains in the nested output directories.
PCIM should use one validated publication model and explicitly check packaged
outputs rather than copy this packaging arrangement.

==== Consequences for the PCIM Plan

Step 5 is retained but divided into verified SDPi parity and additional PCIM
assurance. Parity means shared-model generation, semantic validation during
the build, and packaging of generated documents and JSON. Explicit test-suite
execution, schemas, coverage accounting, release-baseline checks and independent
output comparison are PCIM additions. They remain justified by the requested
traceability of all requirements, but must not be described as existing SDPi
CI features.

For obligation keyword validation, start with an inventory/lint report and
working-group review of compound requirements. Adopt strict matching once the
approved blocks are compatible; do not automatically split or rewrite existing
requirements to satisfy the SDPi lexical rule. In particular, `PCIMR0003` and
`PCIMR0305` each repeat `shall`. Lexical validation aids consistency but cannot
establish semantic atomicity or complete normative coverage.

=== Proposed PCIM Identity Model

The https://wiki.ihe.net/index.php/PCD_OID_Management[IHE DEV OID registry]
reserves `1.3.6.1.4.1.19376.1.6.2.7` for PCIM and lists the existing DPAR,
DPAC and DPAM OIDs. It also lists both `.4.51` / `.1.51.1` and `.4.52` /
`.1.52.1` transaction identifiers. Reservation of the PCIM root is evidence for
the proposal, not confirmation that the following child hierarchy is allocated.

Let `P = 1.3.6.1.4.1.19376.1.6.2.7`. Proposed categories:

|===
|OID / arc |PCIM treatment

|`P`
|Existing PCIM profile identity; also proposed parent for PCIM-owned objects.

|`P.0.<major>.<minor>.<revision>`
|Conformity release identity, after a PCIM version policy is adopted. Do not
infer interoperability guarantees from version numbers alone.

|`P.1`
|Reserve for namespaces/URIs if needed; no artificial namespace for HL7 fields.

|`P.2`
|Reserve for future profile subdivisions; PCIM itself retains `P`.

|`P.3`

==== Step 5 Build Order and Failure Criteria

. *Validate source and model.* Run unit/behavioral tests and model checks
  explicitly in `.github/workflows/latest-master-or-pr-build.yml`; wire the
  checks into the document task graph so local builds also enforce them.
  Validate IDs, references, retirement records, approved coverage dispositions
  and release-baseline changes. CI can validate the ledger's structure and
  recorded mappings; human review establishes that every normative obligation
  has been identified.
. *Generate once.* Produce JSON and the OID appendix include before rendering
  if retaining the Python exporter, or generate both during one AST conversion.
  Replace the current `asciidoctor.finalizedBy(pcimRequirementsJson)` ordering
  with dependencies appropriate to the chosen implementation. A finalizer that
  runs after rendering cannot supply the appendix input to that render.
. *Validate generated artifacts.* Apply committed JSON schemas; compare generated
  fixtures without overwriting expected files; render HTML, then compare its
  requirement/OID rows and anchors with the JSON registry. Compare catalogued
  identities and links, not byte-identical prose across HTML and JSON formats.
  Include tests of duplicate OIDs, retired-ID reuse, unknown targets, section
  movement and empty/malformed normative content.
. *Package only after success.* Verify required HTML, JSON, registry and schema
  files exist and are nonempty in the actual upload directory. Configure upload
  failure when files are missing. Make any asset/ZIP script propagate command
  failures. Keep release packaging behind the same checks; run any future
  tag/release workflow through this path rather than bypassing validation.

Build-time consistency checks and downstream conformance tests remain separate:
a successful specification build does not certify an implementation or prove
that every requirement has a passing test result.

=== Implementation Choices and Review Boundaries

Keep the current Python exporter for the first OID increment. Before expanding
to generated sections and semantic cross-references, evaluate an Asciidoctor
AST/extension adapter against the current line-based parser. Any retained parser
must handle comments, examples, includes and attributes consistently with the
rendered specification; currently it scans only one file and discovers blocks
from matching titles. Do not fork the entire SDPi converter just to obtain OIDs.

Store specification metadata once in AsciiDoc and generate the registry, JSON
and appendix from it. Generate reverse indexes from authored forward references.
Keep normative text authoritative in one place and link repeated discussion to
it. Add focused behavioral checks for leading-zero normalization, preserved
identity after section moves, lifecycle transitions and unresolved relationships.

Working-group decisions needed for release are the delegated root/child
allocations, treatment of existing transaction/message-profile identifiers,
and the requirement change policy. These decisions do not prevent implementing
and reviewing a clearly marked draft model. This assessment makes no external
registry edits, normative edits or claims that conformance testing is complete.
