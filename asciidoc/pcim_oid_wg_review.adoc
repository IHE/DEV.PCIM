== Questions for Decision

=== Q1: Who owns the PCIM subtree and approves allocations?

Can the DEV Technical Committee co-chairs confirm delegation beneath
`1.3.6.1.4.1.19376.1.6.2.7`, identify any existing children, and designate the
PCIM WG allocation steward/reviewer?

Recommendation: retain that reserved root; record explicit delegation and the
child-allocation check. Maintain source-controlled allocations with WG review
and a durable decision reference. Until then, retain proposed status.

Needed evidence: DEV registry or written co-chair decision covering delegation
and pre-existing allocations. Proposed owner: DEV co-chairs with a WG-designated
editor; actual names and dates are to be agreed in the meeting.

=== Q2: Is the proposed hierarchy acceptable?

Approve requirements under `P.10`, the five use cases under `P.9.1` through
`P.9.5`, and Subscription and Filtering under `P.11.1`, subject to Q1?
Keep PCIM itself at `P`, and keep its existing external actor identities?

Recommendation: yes. Leave unused categories without assigned leaves.
Scenarios and use-case-support objects can be allocated when modeled; they are
not manufactured just to fill out the hierarchy. Confirm that one option
identity with actor-specific applicability is appropriate.

Decision must distinguish agreement on structure from confirmation of actual
allocations. A future conformity-release OID needs its own version policy.

=== Q3: Which transaction and message-profile identifiers are authoritative?

For DEV-19, DEV-51 and DEV-52, which OID identifies the transaction, which
identifies the HL7 message profile, and which values are supported legacy
aliases? Do the conflicting `.1.<n>.1` and `.4.<n>.1` values require a CP,
erratum, compatibility guidance, or another action?

Recommendation: preserve all existing wire values in this PR. Nominate an
editor to reconcile registry entries, published PCIM text, message-profile
definitions/validators and deployed use. Record object type and evidence for
each selected canonical value and alias before changing source examples.
Do not assume a registry alias for a transaction establishes a message-profile
alias. The next exporter can support unresolved draft entries but must not
publish them as confirmed allocations.

The DEV registry also reserves `1.3.6.1.4.1.19376.1.6.6.19.1` for the
DEV-19 conformance profile. Include that distinct registry entry in the review;
it is not evidence that current MSH-21 values can be replaced without analysis.

=== Q4: What changes require a new requirement identity?

Approve retaining identity for editorial changes and allocating a new ID/OID
when previously conforming behavior, actor applicability or conditions change?
How should changes of obligation level be reviewed?

Recommendation: explicit compatibility review for level changes; retain exact
release snapshots regardless of identity outcome. Split/merge changes record
all predecessor and replacement links. An OID has no version suffix.

Walkthrough example (hypothetical, not a proposed normative edit): correcting
grammar in `PCIMR0100` preserves its identity; expanding the responsible-observer
obligation to a materially different condition requires review and potentially
a replacement. Test results keep the evaluated release/commit.

=== Q5: How are retired and reserved identifiers managed?

Approve keeping the original ID/OID permanently in a retirement ledger with
last-active/retirement releases, reason, decision reference and replacements?
Remove the old suggestion that retired requirements move to the 9000 range?

Recommendation: yes. The 9000 range is unallocated reserve, not a retirement
destination. Never reuse published IDs. Before the first OID release, establish
a reviewed allocation baseline, including any previously published human IDs.

=== Q6: Can this draft proceed, and what gates PR #2?

May the governance/registry PR merge as clearly proposed authoring policy, or
does the WG require allocation decisions before merge? Who reviews the follow-on
exporter/schema PR? Which unresolved questions must block an official release?

Recommendation: permit draft implementation review while Q1-Q3 remain open;
require confirmed root/leaf allocations and canonical-identifier decisions
before official OID publication. Keep normative cleanup in separately reviewed
changes. PR #2 derives OIDs for the current 33 requirements; it does not claim
the complete normative inventory is finished.
